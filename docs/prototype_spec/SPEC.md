# ジャック＆ヒューズ：正方形ワールド P0 詳細実装仕様

**文書版：0.1.0 / 作成日：2026-09-10 / 実装着手用**  
正式な作品名・リポジトリ名は未決定。本書の `jack_world` とタスク接頭辞 `JWP` は作業用名称である。ヒューズの英語綴りは決めず、内部識別子は `buddy` とする。

> 小さな立方体のジャックと、それより小さい立方体のヒューズで、広い正方形の陸地を探索する。通常のウニを避ける／水バリアで押し返す。異常個体は泡で捕らえ、ヒューズの電撃で撃退する。水と行動用電力を補給し、調査と半固定カメラの演出までを、簡易描画と短いSEで検証する。

本書は**ゲーム実装そのものではない**。現行リポジトリのコード監査、Pyxel実行、iPhone実機試験、性能測定は未実施。付属JSONは初期配置・調整値として作成したもので、数値は実測結果ではない。

## 1. 世界観・表現の固定事項

### 1.1 世界と登場者

タコ文明は移行段階。小共同体があり、人類の遺した街・水場・インフラを部分再利用している。主人公はメンダコの**ジャック**、見習い観察官。バディは汎用デバイスを義体とする電子化人類の**ヒューズ**。近くを飛翔して付き添う。

人類はごく少数が電子生命として、多様な形状の義体の中に存続している。太陽エネルギーで稼働し、夜間は生存維持の省モードとなって会話できない。反復行動をするメンテナンス個体が修理・保守を継続しているため、都市インフラの一部が残る。ただし配管・送電網などの維持は難しく、長く供給停止している場所も多い。

通常のウニは栄養を求めて遺構へ侵入・繁殖し、他生物の侵入に敵対的。ただし非常に鈍く、一般には大きな脅威ではない。高速な例外個体は、この前提を破る異常な存在として扱う。正体や手足の造形はP0では決めない。

### 1.2 表現原則

漫画的・ポップな非言語表現を基本とする。音符、疑問符、驚き記号、少量の粒子、浮遊、軽いポップなどを外付けで付加する。**オノマトペ文字は保留・初期実装対象外**。写実表現・流血表現・大量のスプライト差分を要求しない。

画面全体のフラッシュ、強い揺れ、ヒットストップはP0既定値で無効。軽い集中線は調査のデモで一回試す程度とし、常時発火させない。ヒューズの無言の同行も大事な表現であり、常に会話を表示しない。

立方体ジャック、小立方体ヒューズ、通常ウニ2体、異常ウニ1体、少数の平面プロップ、短い障害物、水補給2か所、供給停止蛇口1か所、充電地点2か所、調査対象、全景ゾーン1か所、パンのデバッグデモ、5種類のSEを含める。

## 3. マップ仕様

### 3.1 寸法と座標

```text
X : 地面上の第1軸
Y : 高さ。正が上
Z : 地面上の第2軸

1セル = 32 world units
32×32セル = 1024×1024 world units
地面 = 0 <= X <= 1024, Y = 0, 0 <= Z <= 1024
セルインデックス = (cell_x, cell_z)、各0〜31
セル中心 = ((cell_x + 0.5)*32, 0, (cell_z + 0.5)*32)
```

JSONの `position` は原則として足元・物体ルート。高さと地面奥行きを両方 `y` と呼ばない。ゲームロジック・レンダラーともY-upで統一する。セル検索は内側の点について半開区間で扱い、上端境界の1024を誤ってセル32に割り当てない。

### 3.2 地面の構成

全面歩行可能な平地一枚から始める。少数の障害物だけを上に置く。壁による区画封鎖、迷路、扉、進行フラグによる遮断を作らない。セルは配置・将来の手書きマップ受け入れ単位であり、プレイヤーがセル単位で移動するわけではない。

当たり判定の外周は世界境界そのもの。厚い壁を32個並べて代用しない。外側を描く必要が生じた場合は無地の背景と境界線で表し、歩行可能な地面に見せかけない。

### 3.3 配置の考え方

開始位置は `(160,0,160)`。開始地点近くに水補給・日なた・案内物を置き、東方向に通常ウニと停止蛇口、その先に二つ目の補給地点と異常個体を離して置く。北東側に全景ゾーン、西〜中央側に重なり確認用プロップを置く。具体的な座標は付属JSONを正本とする。

配置間の距離は検証用。正式なステージの物語的地理ではない。開始地点からすべての補給地点へ、資源ゼロでも歩いて戻れる。異常個体を倒さなくてもマップを一周できる。

### 3.4 安全地帯

開始地点付近と東側補給地点付近に安全円を置く。安全円は壁ではなく、敵が入れない行動境界。敵中心が「安全円半径＋敵半径」より内側へ侵入しないよう移動を制限する。追跡・ダッシュ・押し返しにも適用する。開始位置に敵を生成しない。

プレイヤーは自由に出入りできる。安全円に入ったら敵は接触攻撃をやめ、自分の位置から待機／帰還へ移る。ワープさせない。水や電力がなくても、ここまで逃げれば補給できる。

### 3.5 将来の手書きマップへの接続

`ground.default_walkable` と `cell_overrides` を保持する。P0では全セル歩行可・override空。手書きからのセル座標、通行不可、高さ、配置、カメラ領域への変換は後続作業とし、画像認識をゲーム内に作らない。P0ではナビゲーショングラフやA*を必須にしない。

## 4. 基本設計と時間管理

### 4.1 状態・描画・入力の分離

ゲームモデルはPyxelから独立させる。描画クラスに水・電力・敵状態の変更を書かない。入力は「移動意図」「防御保持」「アクション要求」「調査要求」に変換してモデルへ渡す。モデルの結果イベントをSEと視覚演出が購読する。

過剰な汎用ECS・DIコンテナ・非同期イベントバスは導入しない。小さな型付きdataclass、enum、明示的なSystem呼び出しで足りる。

### 4.2 時間

ゲーム更新は60Hzの固定刻み。通常描画目標60fps、比較用30fps。速度・消費量・持続時間は秒ベースの設定から計算する。

ホストのupdateコールバックで単調時刻を取得し、accumulatorへ加算。1ステップは1/60秒。1コールバック最大6ステップ、入力elapsed最大0.1秒。過負荷で時間を捨てた場合はカウンタを残し、黙って「速度不変」と報告しない。

- `world_tick`：移動、敵、泡寿命、資源等のゲーム時間。モーダル・ポーズで止まる。
- `presentation_time`：UIとカメラ補間用。調査パネル中も進む。タブ非表示では止める。
- 一回性の入力は、次のシミュレーションステップまで小さなキューに保持し、一度だけ消費する。
- 同一コールバック内の複数ステップで発射・放電を複製しない。
- 非表示から復帰時はaccumulatorと前回時刻をリセット。非表示だった時間を一気に追いつかせない。
- `pyxel.frame_count` を水消費や捕獲寿命の唯一の時計にしない。

この方式は負荷が許す通常状態の30/60fps比較で同じシミュレーション時間を維持するための設計であり、処理能力を超える状況で無条件に60Hzを保証するものではない。

### 4.3 更新順序

```text
ホスト状態・入力採取
  → UI入力所有権の解決
  → モーダル開始要求の安全判定
  → fixed steps（worldが止まっていないとき）
      1. 前ステップで期限切れの状態を解消
      2. 一回性コマンドを検証・実行（資源消費はここ）
      3. プレイヤー移動、敵状態と移動
      4. 泡移動とsweep衝突 → 捕獲
      5. バリア押し返し → 未防御接触
      6. ヒューズ追従・調査候補・ゾーントリガー
      7. 状態時間を進める／イベントを確定
  → モーダル・カメラ・表示演出の更新
  → そのコールバックのイベントからSE要求を集約
  → 描画用スナップショットを準備
```

捕獲が成立した敵は、そのステップの以後の接触ダメージ候補から除く。バリアが有効だった時間は消費を先に計算し、不足分を負の水量にしない。複数の結果が同時に生じても、同じ対象に撃退を二重適用しない。

## 5. 入力契約

### 5.1 PC

| 操作 | キー |
|---|---|
| 移動 | 矢印 / WASD |
| 水バリア | Space保持 |
| 泡／電撃の文脈アクション | Xを新たに押す |
| 調査・補給開始 | Eを新たに押す |
| パネルを進める／閉じる | Enterまたは画面ボタン |
| ポーズ | Escape |
| 音のON/OFF | M |
| デバッグ表示 | F1 |

Escapeはゲーム内ポーズであり即アプリ終了にしない。Pyxel初期化のquit keyを無効にする等、採用版APIで確認する [S1]。マウスはスマホ同様のポインター入力も試せる。WASDのSと音設定を衝突させない。

### 5.2 スマホ：一接触で成立する入力

ワールド面：ドラッグで歩行、その場の長押しでバリア。右側に文脈アクションボタン一つ。調査は近い対象のマーカーまたは調査ボタンをタップ。初期版は二本指同時操作を要求しない。

入力状態：`IDLE / WORLD_PENDING / MOVE / BARRIER / UI_CAPTURE / WAIT_ALL_RELEASE`。

1. タッチ開始時に、モーダルUI → HUD → 調査マーカー → ワールドの順で所有者を決める。
2. ワールドなら `WORLD_PENDING`。押下点、最大移動量、開始時刻を記録。
3. 閾値以上動いたら `MOVE` に確定。長押し判定よりドラッグ判定を先に評価する。
4. 移動閾値未満のまま0.22秒経過したら `BARRIER`。
5. `MOVE` は指を止めても `BARRIER` にならない。`BARRIER` は指を動かしても歩行にならない。
6. 離したらその所有者だけが解放される。UIを閉じた同じ指で歩行・発射を開始しない。
7. 画面回転、ポーズ、OS割り込み、非表示、キャンセルで保持を解除し、必要に応じて `WAIT_ALL_RELEASE` にする。

「画面を押している時間が長い」だけで、歩行中に防御が出ないことを必須とする。

### 5.3 ドラッグ移動

入力強度は原点からの距離に応じて0〜1。基準解像度でdeadzone8、最大48px。原点は一接触中固定。超過分は大きさだけclampし、初期版は原点追従をしない。

```text
a = clamp((r - deadzone)/(max_radius - deadzone), 0, 1)
```

UI寸法と閾値は `logical_height/236` で基準値からスケールする。実際のタッチ対象は44 CSS px以上を本プロジェクトの初期目標とし、CanvasのCSS倍率から論理サイズへ換算する。この44は性能値や端末の物理寸法ではなく、試験用の操作寸法である。

### 5.4 文脈アクションの確定

- 捕獲対象なし：泡。射程内・視線の通る異常個体一体を候補にする。
- 捕獲対象あり：電撃。捕獲対象を固定して候補とする。
- 泡飛翔中：追加発射不可。
- 電力不足等：不可表示。ただし押下したときに理由を短く示す。

画面に**最後に描いた**アクション種別・対象IDを、押下開始時にトークンとして固定する。指を離した時に表示状態が変わっていたらキャンセルする。同じ接触を泡発射と電撃の両方に使わない。電撃には必ず新しい押下が必要。

敵候補のマーカーは一体だけ。選択は「画面内／射程内／LOSあり」を満たす異常個体のうち距離最小、同距離なら安定ID順。画面外の敵を勝手に狙わない。捕獲中に別個体へ自動乗り換えしない。

バリア保持中は泡・電撃を受け付けない。PCでも防御を解除してからXを押す。泡・電撃成立時は0.15秒の短い移動ロック。失敗した操作では移動ロックしない。

### 5.5 複数接触・Webブリッジ

Pyxel公開入力で同時接触点を当然に取得できると仮定しない [S1]。採用ランタイムの実際の入力経路をJWP000/002で確認する。

P0は一接触を所有し、二本目が検出された場合は新しい行動を開始しない。安全な既定動作はすべての保持を解除し、全接触終了まで待つ。互換マウスイベントと独自Pointer Eventsを二重に処理しない [S6]。

ホストから必要な入力情報は、ポインターID・座標・開始／終了／キャンセル、表示領域、Safe Area、visibility。受け渡し方法は採用Pyxel Web版で動作するものを一度だけ実証し、アダプターへ隔離する。未確認の `import js` や私的ランタイム変数を当然に使えるものとして実装しない。

## 6. プレイヤー・衝突・接触

### 6.1 ジャック

ルートは足元中央。XZ半幅8、高さ16の立方体を表示する。接触形状は地面上のAABB。浮遊は見た目だけのYオフセットであり、ルートY=0・衝突・水消費・攻撃範囲は変化しない。

移動速度96 world units/秒を初期値とし、慣性なし。指・キーを離した次のstepで通常移動速度を0にする。斜めも同じ最大速。移動距離の記録は衝突解決後の実移動量で行う。

### 6.2 画面方向からワールド方向への変換

カメラの現在の向きに対して、画面右入力は投影像の右へ、上入力は投影像の上へ向かうようにする。world X/Zへ直接キーを割り当てない。

第8章の投影を `s(P)` として、プレイヤー位置における2×2ヤコビアン `J = ∂(sx,sy)/∂(X,Z)` を一回求める。

```text
q = (screen_input_x, screen_input_y)  # 画面下が正
v_raw = inverse(J) * q
v_world = normalize(v_raw) * move_speed * input_strength
```

変換後に正規化し、奥行き方向だけ速度を上げない。入力ゼロ、near外、行列がほぼ特異の場合は移動ゼロと診断情報。行列が壊れたときに別の軸へ突然進ませない。

初版は数値微分でもよいが、中央差分等で一貫性をテストする。解析式を使う場合、`r=R·(P-C), u=U·(P-C), d=F·(P-C)` として：

```text
∂sx/∂a =  f * (R_a*d - r*F_a) / d²
∂sy/∂a = -f * (U_a*d - u*F_a) / d²   (a = X,Z)
```

カメラ補間中も最後に表示したカメラの基底で入力を解釈する。仮想スティック原点はカメラが動いても画面上で飛ばさない。

### 6.3 衝突解決

地面境界と静的AABBに対して、移動量を分割してX/Z軸別に解決し、壁に沿って滑る。1分割の水平移動は最大4 world unitsを目安にし、押し返し・ダッシュでも薄い障害物を飛び越さない。泡だけは別途sweep衝突を必須にする。

プレイヤー中心の範囲は `[half_x, map_width-half_x]` と `[half_z, map_depth-half_z]`。中心だけ境界内でも、体半分が外に出る処理を避ける。

すべての静的障害物を毎step全探索せず、移動前後のswept AABBに重なるチャンクを問う。描画カリングの結果を衝突データの有無に使用しない。

### 6.4 敵への未防御接触

P0にはHP・死亡を入れない。接触すると安全な方向へ短いノックバック、0.2秒の操作停止、1秒の接触無敵を付け、デバッグの被接触回数を増やす。水・電力を勝手に奪わない。音がなくても点滅／位置変化で接触が分かる。

判定は敵円とプレイヤーAABBの最近点距離等、仕様の形状に合わせて行う。完全に同じ中心で法線が取れない場合は直前の移動方向の逆、なければ安定IDから決まる方向へ退避する。NaNを出さない。

敵同士の精密押し合いは対象外。接触判定はプレイヤー対敵だけでよい。捕獲済み・撃退済み・休憩状態の敵から不意に接触イベントを出さない。

## 7. ヒューズ

ジャックより小さい一辺6の立方体。高さ26を中心に小さく上下する。物理的な障害物衝突は持たない補助アクターとする。

通常の目標位置は、地面上の画面右方向 `R_ground` と地面前方向 `G` を使い、

```text
buddy_goal = player_ground - 20*R_ground - 12*G + (0,26,0)
```

とする。Y成分の意味は地面からの高さ。指数追従 `1-exp(-dt/tau)`、tau=0.18秒を初期値にする。ルート位置が80以上離れるのは異常として、スタート／リセット等の瞬間だけ安全な位置へ再配置する。通常飛行中の突然のワープを見せない。

**P0の割り切り：** 飛行ルート探索はしない。壁上を通過できる。描画は必ずワールド深度に参加し、常時最前面のHUDにしない。小さな遮蔽物との交差は配置と高さで避ける。将来の飛行衝突・経路探索がなくてもP0を完了できる。

捕獲成功時は短い注目モーション、電撃成立時は短い姿勢／色変化だけを追加する。実際に目標近くまで移動し終えることを放電成立の条件にしない。戦闘判定を追従演出の遅延に依存させない。

## 8. 半固定カメラ

### 8.1 カメラ表現

カメラ状態を `target: Vec3 / yaw / pitch / distance / screen_anchor` として持つ。初期yaw20°、pitch25°、水平FOV38°、距離480。yawはワールド+Z方向を0°として+X側へ回る角度、pitchは水平を0°として下を向く角度と定義する。

```text
F = (cos(pitch)*sin(yaw), -sin(pitch), cos(pitch)*cos(yaw))
R = (cos(yaw), 0, -sin(yaw))
U = (sin(pitch)*sin(yaw), cos(pitch), sin(pitch)*cos(yaw))
C = target - distance*F

V = P-C
r = dot(V,R); u = dot(V,U); d = dot(V,F)
f = viewport_width / (2*tan(horizontal_fov/2))
sx = viewport_left + anchor_x*viewport_width + f*r/d
sy = viewport_top  + anchor_y*viewport_height - f*u/d
```

ここでF/R/Uは正規直交するカメラ前・右・上。角度のdegree/radian変換をAPI境界で統一する。画面全体のCSS拡大とカメラのdistance変更を混同しない。

`distance = base_distance / zoom`。FOVはズーム演出では変えない。ズームしても衝突サイズ、射程、移動速、水消費は変えない。near8、far1800。画面サイズやズームで近接クリップ条件を別々に持たない。

### 8.2 状態と優先順位

| 構図 | 優先度 | ゲーム時間 |
|---|---:|---|
| FOLLOW | 0 | 進む |
| OVERVIEW / AreaCamera | 20 | 進む |
| EVENT_PAN | 40 | P0デモでは止める |
| FOCUS / 調査・補給 | 60 | 止める |
| アプリの非表示・ポーズ | 全体に優先 | 止める |

`RETURN` は演出後の補間過程であって、復帰先を固定した独立の世界状態にしない。戻り先は**今のプレイヤー位置に対応するAreaCamera、なければFOLLOW**を再解決する。調査前の古い座標へ戻さない。

プレイヤーには手動パン、ピンチ、自由回転、ズームボタンを提供しない。FOV比較や有限個の角度切替はデバッグ専用。通常プレイの操作表に載せない。

### 8.3 FOLLOW

基準アンカーは画面幅50%、高さ58%。画面中心付近に幅18%、高さ12%のデッドゾーンを設け、プレイヤーの投影位置が外へ出た分だけ注視点を地面上で補正する。

補正は投影のヤコビアンで画面残差を地面変位に戻し、指数補間する。具体的には `e = s(player) - clamp_to_deadzone(s(player))`、`delta_target_xz = inverse(J) * e`、`target_xz += (1-exp(-dt/tau))*delta_target_xz` とする。注視点を動かしたことによるプレイヤー投影像の変化は近似的に `delta_s = -J*delta_target_xz` なので、この符号になる。地面と平行にカメラと注視点を同時移動するので、投影像の移動方向に対して補正の符号が逆になることをテストする。実装の契約は「プレイヤーが右へ外れたら、カメラが右側を追い、画面内へ戻す」。

初期look-aheadはOFF。デッドゾーンが安定した後、実移動速度×0.15秒を上限18 world unitsで制限した先読みを比較できるようにする。壁に押しつけた入力では先読みしない。

境界付近では注視点を地面範囲へclampする。画面の全領域を必ず地面内へ収めるための複雑な逆解はP0不要。地面外の背景が見えることは許容するが、プレイヤーを画面外へ追い出すclampはしない。

### 8.4 OVERVIEW

JSONの矩形内へ**プレイヤーが**入ると発動する。カメラ自身が領域に入っても発動しない。注視点 `(768,0,768)`、zoom0.70、yaw35°へ0.8秒で補間し、入域中は維持する。歩行・バリア・攻撃は止めない。

退出は矩形を32広げた範囲から出たとき。境界上の往復でモードが高速に切り替わらないようヒステリシスを入れる。ゾーンは重なった場合にpriority最大、同値なら安定ID順。一度に一つだけベース構図を解決する。

このゾーンは「付近の広場を引いて見せる」ものであり、1024四方すべてが一画面に入る必要はない。ジャックと操作対象が小さすぎる場合は、試験結果に基づいてzoomを調整する。

### 8.5 FOCUS

調査対象の高さ中心をO、ジャックの見た目中心をPとして、`T = 0.35P + 0.65O`、zoom1.30を初期値にする。下部パネルと重ならないよう画面アンカーを `(0.5,0.40)` に移す。対象だけに寄りすぎず、二人との関係を残す。

角度は原則として解決済みベース構図を継承。0.35秒の補間、終了時0.5秒で最新ベース構図へ戻す。パネルが出ている間、敵、泡寿命、資源消費、ゲーム時計は止まる。カメラとUIだけ進む。

### 8.6 EVENT_PAN と補間

イベント用Cueは `target / zoom / optional yaw,pitch / blend_sec / hold_sec`。P0の `pan_demo` はデバッグからのみ起動する。メンテナンス個体→観察地点→現在ベース構図へ移る。プレイ進行に必要な長い自動演出は作らない。

補間は区間開始時の実カメラ状態を保持し、`smoothstep(t)=t²(3-2t)` を使う。yawだけは最短角差。途中でFOCUSへ割り込まれた場合は、現在の補間結果を次の始点にする。元々の始点へ戻ってから再開しない。

カメラの見た目変化でゲーム座標、敵の状態、SE回数を変えない。自由回り込みで裏側まで見せることは要求しない。

## 9. 描画・スプライト・遮蔽

### 9.1 パイプライン

```text
背景
→ 可視地面チャンクと境界
→ 地面に貼り付く影・小ディテール
→ 奥行き順のワールド描画キュー
   （ジャック、ヒューズ、敵、プロップ、泡を同じ系へ入れる）
→ 必要時のみ遮蔽されたジャックの簡易輪郭
→ 読みやすさ優先の調査マーカー／感情記号
→ 小規模なスクリーン演出
→ HUD、パネル、ポーズ、デバッグ
```

**「オブジェクトを全部描いてからキャラクターを描く」は禁止。** ジャックもヒューズもワールドの描画順へ参加する。水バリアや泡のようなまとわりつく図形は、対象の描画コマンドに前後の小サブレイヤーとして接続する。

### 9.2 深度ソート

基準深度は `d = dot(anchor-C,F)`。降順（奥→手前）。ワールドZだけで並べない。床上スプライト・ジャックは接地ルートをsort anchorとし、浮遊するヒューズは実際の飛翔ルートを使う。見た目だけの小さなbobをソート深度へ入れて順序を振動させない。

同じ深度の安定化は `(-depth, layer_bias, entity_id)` 等で行う。biasを「常に主人公が前」になるほど大きくしない。微妙に近い深度を過度に丸めると逆転が遅れるので、同深度扱いのepsilonは最小限にする。

毎描画時に**可視候補のみ**ソートする。数十個なら必ず軽い、と断定しない。描画・投影・塗り面積も含めて実測する。

### 9.3 立方体・板ポリゴン

立方体はワールド8頂点を共有カメラで投影し、表向き面だけを平塗りする。面は内部で奥→手前に並べる。大きな壁を一体として扱うとPainter順が破綻し得るため、壁の描画は32〜64単位程度の短い部分へ分割し、衝突用AABBとは分けてよい。

この方式は任意の3D交差形状を正しく描く保証ではない。P0では交差する巨大面、橋の上下、建物内部を作らない。必要なら分割で対処し、汎用Z-bufferを新規実装しない。

### 9.4 スプライト

将来の木、看板、メンダコ等は2Dスプライト＋ワールド位置で扱う。P0でも木3本等を簡単な2Dプレースホルダーとして用意し、差し替え経路を試す。既存素材がなければ起動時に16色の短い画像配列から一度だけ作る。画像生成や完成美術を待たない。

`SpriteDef` の必要項目：画像領域、元画像サイズ、世界サイズ、足元アンカー、colkey、フレーム列、周期、visual bounds、sort anchor。

拡大率はカメラ距離から一貫して求める。キャラクターだけ別の倍率制限を掛けない。現在確認した公開APIの `blt` は一様scaleとrotateを持つが、採用版との差を確認する [S1]。`scale_x/scale_y` を存在しないキーワードとして渡さない。伸縮はP0では位置・影・少数の差分に限定できる。

`blt` の変形中心と足元アンカーを混同しない。中心基準の拡大の場合、出力中心を `projected_anchor - scale*(anchor_in_source-source_center)` へ合わせる等のアダプターで調整し、倍率を変えても足元がずれないテストを行う。

### 9.5 near/farクリップ

頂点がnearをまたぐ地面・面を、そのまま `f/d` に入れない。カメラ空間でnear/farへクリップし、できた多角形を三角形分割する。スクリーンのclipも併用。負深度、0除算、無限大の画面座標を描画関数へ渡さない。

### 9.6 影と遮蔽輪郭

ジャックの影は地面Y=0に固定。表示だけの浮遊と逆向きに、ごく小さく幅を変える。厳密な光源計算は不要で、影も同じカメラで位置と寸法を変える。

遮蔽はP0では「自分より手前に描かれるoccluderの画面矩形と、ジャックの矩形が重なる」簡易判定でよい。該当時だけジャックの細い輪郭を最後に描く。葉の穴などのピクセル単位の正確さは保証しない。誤検出の程度は記録する。

常時シルエットを表示したり、キャラ全体を常に最前面へ描き直したりしない。市松半透明のために大きなスプライト全画素を毎フレームPython処理することも避ける。

## 10. ウニの状態機械

### 10.1 共通事項

半径10、地面上の円形接触範囲。P0は通常2体、異常1体のみ。敵に一般的なHPバーは持たせない。手足・体型などの完成デザインは不要で、円＋短い棘と状態色で識別する。色だけに頼らず、異常個体は予兆マーカーも使う。

地面境界・静的障害物・安全地帯を越えない。経路探索なし。詰まった敵は待機または帰還へ切り替える。補給地点への道を封鎖する設計にしない。

### 10.2 通常個体

`IDLE → APPROACH → REPELLED → REST → IDLE/APPROACH`。活動範囲外なら `RETURN_HOME`。

自発移動は6 world units/秒。ジャックの96に対して十分遅い初期値であり、怖い高速突進を通常個体へ追加しない。80以内で気づき、遅く近づく。自宅から128を越えたら帰還する。

バリアが当たると40だけ押し返され、2秒休む。これは外力による移動であって、自発的な高速行動ではない。回り道か押し返しで通過できることを確認する。泡の自動照準候補にはしない。

### 10.3 異常個体

`IDLE → APPROACH → WINDUP → DASH → RECOVER` を基本にし、どこからでも捕獲可能な状態では `CAPTURED` へ、電撃成立で `DEFEATED` へ遷移できる。

初期値：接近32、ダッシュ180 world units/秒。検知128、溜め開始距離112、予兆0.75秒、ダッシュ0.45秒、硬直1.2秒。

- 予兆開始時に進行方向を確定し、小さなラインで示す。
- ダッシュ中は追尾しない。途中で直角に向き直らない。
- 障害物・安全地帯に当たったら止まり、RECOVERへ。
- 初遭遇で即被弾させない。離れた位置で予兆を認識できるようにする。
- プレイヤーが自宅から160以上離れていく場合は追跡をやめる。戻るときは通常接近速を使う。
- バリアは24だけ押し返して0.8秒の間を作るが、撃退しない。

安全に狙えるのは主にWINDUP/RECOVER。ただし技術上はAPPROACH/DASHでも、泡が実際に命中すれば捕獲してよい。素早さを理由に無敵フレームを追加しない。

### 10.4 捕獲・解除・撃退

`CAPTURED` は4秒。移動・接触攻撃・AIを止める。見た目だけ泡内へ浮かせ、ゲーム上の捕獲位置は維持する。接触で通路を塞がない。

期限切れの場合は `RECOVER` へ移り、少なくとも0.5秒は再攻撃しない。期限は世界時計で管理し、カメラ外へ出ても凍結しない。捕獲個体は可視性に関係なく期限までアクティブ対象にpinする。

電撃成功時は `DEFEATED`、接触とAIを即停止。短い退場演出の後に消える。P0はシーンをリセットするまで再出現しない。倒しても経験値・アイテムは出さない。

## 11. 水バリア・泡・電撃と資源

### 11.1 水と電力

水の最大100、初期100。行動用電力の最大60、初期60。電力は生存維持用ではなく、電撃等に使える余剰枠として扱う。行動用電力が0でも、昼のヒューズの同行・通常会話を止めない。

歩行、待機、通常の浮遊では消費しない。P0は自動回復なし。最大値超過・負値を禁止。水バリア以外の離散コストは、成功条件をすべて確認してから一度だけ引く。

### 11.2 水バリア

保持中に半径30の防御判定。展開中はジャック停止。毎秒10の水を消費する。最低1step分の水が足りるときだけそのstepで有効にし、不足なら残量を0にclampして解除。最後のわずかな水で長時間無敵にならない。

泡の発射とは別の能力で、放したことを発射トリガーにしない。敵との接触時には敵ごとの状態を `REPELLED` に変え、一回だけ `barrier_repelled` を出す。同じ敵に毎step押し返しやSEを重ねない。

水が尽きたら一度だけ不足を通知し、押したままの状態から自動再展開しない。新たな保持開始が必要。バリアは全方向なので照準を要求しない。

### 11.3 泡発射

一発のコスト12。射程128、選択射程112、速度240、半径10。最大飛翔泡1、最大捕獲1。泡はターゲットを選んだ発射時点の方向へ直進し、追尾しない。見えていた目標でも、その後移動すれば外れてよい。

発射前に、世界停止中でない、バリア中でない、クールダウン完了、対象が有効、射程・LOS・画面内、水量十分、プール空きありを検証。成功したら泡を生成して水を消費し、`bubble_fired` を一回出す。

敵に命中すると `CAPTURED` と `enemy_captured`。壁・射程限界で消滅しても、発射済みの水は戻さない。未発射の失敗では水を消費しない。弾の色やSEで「発射した」と「命中した」を区別する。

衝突は泡と敵の相対移動を考慮したsweep。少なくとも1stepの線分に対して半径和の円との交差時刻を解き、壁は半径分拡張したAABBとの線分交差を行う。**最も早い衝突を一つだけ**解決する。同時なら壁優先等の規則を固定する。終点だけの重なり判定で高速個体をすり抜けさせない。

### 11.4 電撃

プレイヤーから144以内、ヒューズがプレイヤーから80以内、対象が捕獲中で最後の描画でも画面内、対象までのLOSあり、昼、電力20以上、移動ロック等の禁止状態でないことを確認する。ここでのLOSはプレイヤーと対象の地面上線分に対する保守的判定とし、ヒューズが壁の上へ飛ぶ演出で攻撃判定を抜けさせない。

成功時に一つの処理として、電力を20減らし、対象をDEFEATEDにし、`discharge_succeeded` を一回出す。視覚上の電撃は0.16秒だが、判定の成立を演出終了まで遅らせない。

捕獲解除期限を迎えた後の押下、壁越し、範囲外、電力不足では成立しない。UIに映っていた対象でも、実行時に再検証する。成立しないときに電力だけ減らさない。

電撃で捕獲済みの敵をまとめて自動撃破する機能、連鎖、帯電水面、実際の導電シミュレーションは対象外。

### 11.5 電力を使わず逃げる

捕獲したまま通過し、電撃を使わず逃げることを許可する。捕獲成立時の自動放電はしない。カメラが外れたことを理由に泡を永久化しない。

夜は電撃不可という実装フックを設けるが、P0の時間帯は昼固定。夜の特殊戦闘やヒューズの搭乗アニメは作らない。

### 11.6 被接触・撃退と世界観

P0の「撃退」はゲーム上の排除状態であって、ウニの死亡・爆散という設定を追加しない。通常個体は押し返されて休むだけ。異常個体は短く退場し、正体や結末は描写しない。

## 12. 調査・水補給・充電

### 12.1 調査候補

48以内・LOSあり・画面内の対象から一つだけ選び、小さなマーカーを表示する。距離最小、同距離ならID順。敵の照準マーカーと見た目を区別する。最後に描いたマーカーへのクリックを、次のカメラ位置で勝手に別対象へ解釈しない。

安全地帯外では、96以内に撃退されていない敵がいる間は調査・補給を開始できない。捕獲中の敵もこの判定に含む。捕獲して調査パネルを開き、寿命を都合よく止め続ける手段にしない。

### 12.2 調査パネル

世界を止め、FOCUS構図へ寄る。見出しと短い本文、閉じるボタン。本文はP0では最大2〜3行を基本とし、長文ページ送りを必須にしない。既読IDをシーン内の集合へ記録する。記録数表示は任意のデバッグ用で、クエスト進行条件にはしない。

日本語は既存プロジェクトの適切な権利・パッケージ設定を持つフォント資産があれば再利用し、使用版の `Font.text_width` 等で実測レイアウトする [S1]。OS内の個人環境フォントへ絶対パス依存しない。E0では同梱JSONのASCII文を使用してよい。P0の報告では日本語表示が確認済みか、ASCII暫定かを区別する。本仕様パックにはフォントファイルを含めない。

閉じる入力はパネルが消えた後の移動・バリアへ漏らさない。復帰カメラ補間中に移動を再開する場合も、画面入力方向を保つ。

### 12.3 補給

水補給地点はworkingなら「補給」、stoppedなら供給停止説明のみ。working地点では確認操作で0.8秒の短い補給演出を開始し、完了時に水を最大値へする。充電地点は昼なら1.2秒で行動用電力を最大値へする。日なたは架空の充電設備というより、安全に光を受けられる休憩場所の試験マーカーでよい。

処理中は世界停止、UI進行のみ。途中で中止した場合は残量を元のままにする。完了をまたぐキャンセルと補給を二重に適用しない。長押しや連打を要求しない。

パッシブなリアル時間待ち、複雑な日照遮蔽、配電網のシミュレーション、補給料金、回数制限はP0では導入しない。供給停止蛇口を、近くをクリックしただけで復旧させない。

## 13. 演出とSE

### 13.1 ゲームイベントを境界にする

最小イベント構造：`event_id, world_tick, kind, actor_id, target_id, world_position, payload`。`event_id` はセッション内で一意な連番。イベントはモデルが状態を確定した後に発行する。描画・SEの成否でゲーム判定を巻き戻さない。

| イベント | 発行条件 | 視覚反応 | SE |
|---|---|---|---|
| `bubble_fired` | 泡生成と水消費が成立 | 小さな発射リング | 発射 |
| `enemy_captured` | 泡の実命中で捕獲へ遷移 | 囲む輪、軽い浮き | 捕獲成功 |
| `barrier_repelled` | 押し返しへ状態遷移 | 水滴少数 | 押し返し |
| `discharge_succeeded` | 電力消費と撃退が成立 | 短い折れ線電撃 | 電撃撃退成功 |
| `action_denied` | 明示的な操作が実行不可 | ボタンの短い反応／理由アイコン | 使用不可 |

補給完了、調査開始、敵の退場、被接触等は別のイベントにしてよいが、初期SEは上記5種類のみ必須。`enemy_defeated` と `discharge_succeeded` の両方から同じSEを二重再生しない。

`action_denied.payload.reason` は `insufficient_water / insufficient_energy / no_target / target_changed / blocked / out_of_range / cooldown / busy / night` 等。入力を押していないのに毎フレーム不可イベントを作らない。

### 13.2 外付け視覚演出

`EffectCue` は `event kind → effect name, anchor, lifetime, priority` の小さな定義表とする。全ゲーム機能を任意文字列スクリプトへ移すような演出言語は作らない。

空間を分離する。

- `WORLD`：泡、水滴、影。ワールド座標を持ち、投影・深度順へ参加。
- `ACTOR_OVERLAY`：頭上の「?」「!」「♪」。毎フレーム対象アンカーを投影し、最小の読みやすい大きさを確保。
- `SCREEN`：集中線。UIの下、世界の上。

文字フォントで出せると決めつけず、記号は小さなスプライトまたは線分で描けるようにする。オノマトペ文章は追加しない。

上限は粒子64、感情記号8、画面演出1。1イベントの粒子は最大8。満杯なら低優先度の演出を省略し、泡そのものや当たり判定を消さない。プールは単純な固定長／再利用構造で十分。近接草の反応は同じ草へ連続発火しないようクールダウンを入れる。

集中線は12本程度、開始時に端点や位相を決める。毎フレーム乱数で点滅させない。強い全画面フラッシュを初期設定で入れない。

### 13.3 音の役割と制約

音は短い合成SEだけ。BGM、常時バリア音、環境ループ、外部WAV/OGGは不要。既存プロジェクトの音声層を再利用する場合も、BGMを自動で開始しない。

現在確認したPyxel公開仕様には4チャネルとSound/再生APIがある [S1,S2]。P0はチャネルを増設せず、0=発射、1=命中・成功、2=不可、3=未使用に固定する。具体的な音程列は実装・試聴で作り、未試聴音を「適切」と断言しない。

優先度：電撃80、捕獲60、押し返し30、発射10、不可5。同一チャネルに同じ描画コールバック内で複数要求があれば最高優先度を一つだけ採用する。同優先度はイベント順で安定化。過去の低優先度音をキューで後から鳴らさない。

SE用のクールダウンは演出側の時刻で管理する。不可音は最低0.25秒、押し返し音は最低0.1秒の間隔。同一event_idは一度だけ処理。ゲーム内の押し返し自体の成否を、音のクールダウンで制御しない。

音のON/OFFは常に操作可能。ミュートにしても、ゲーム結果・資源・イベント列は変えない。非表示・中断時は再生を止め、復帰後に古いイベントを再生しない。

### 13.4 Web音声の開始

最初に「開始」操作を置き、音ON/OFFの選択とランタイムの音声開始処理をそのユーザー操作へ接続する。起動直後の自動再生成功を前提にしない。開始後に短い試験音を鳴らせるボタンを設定画面へ置く。

Pyxel Web側の実際の初期化経路と採用版の制約を確認し、存在未確認のAudioContext参照を固定しない。API呼び出し成功だけで「iPhoneで聞こえた」と扱わない。音声が使用できない場合も視覚フィードバックでゲームを継続し、音声は未確認／不具合として報告する。

## 14. カリング・休眠・性能

### 14.1 描画対象と更新対象を独立させる

| 種類 | 画面内 | 画面外だが近距離 | 遠方 |
|---|---|---|---|
| 静的装飾 | 描画のみ | 個別更新なし | 個別更新なし |
| 環境アニメ | 表示時に現在フレームを算出 | タイマー更新不要 | タイマー更新不要 |
| プレイヤー・ヒューズ | 更新・描画 | 常にゲーム上必要な更新 | 通常は遠方にならない |
| 敵 | プレイヤー近傍なら更新 | 衝突・AIを必要な範囲で更新 | 待機状態なら休眠 |
| 泡・捕獲期限 | 寿命と判定を更新 | 寿命と判定を更新 | 有効中はpin、期限後解放 |
| 非本質的な粒子 | 上限内で表示 | 生成抑止／破棄可 | 生成しない |

「画面外のものは描画しない」は守る。ただし「画面外の敵の判定を消す」「捕獲の寿命を止める」「壁の衝突を消す」は行わない。カメラを動かすだけでゲーム結果を変えない。

### 14.2 空間分割

XZを128四方で分割し、32セル四方のP0では8×8=64チャンク。静的物体は読み込み時に登録。動的物体は所属が変わったときだけ更新する。大きな物体は境界にかかるすべてのセルへ登録するか、照会範囲を保守的に拡張する。

描画は有限near/farを持つ視錐台とチャンクの3D AABBで候補を作る。チャンクboundsは最高スプライト高さと幅の張り出しを含む。地面上の足元だけが画面外という理由で、高い木の上半分を消さない。

P0なら64チャンクへの粗判定から始めてよい。その後、候補の物体だけvisual boundsを投影して画面交差を調べる。画面には基準24pxの余裕を含めて急なポッピングを防ぐ。詳細なBVH・Octreeは不要。

カメラの地面逆投影だけを唯一の候補領域にすると、高いスプライトや近接クリップで漏れ得る。採用する場合も高さ・外形の余裕、far制限、nearと平行なレイへの対策を必須にする。

### 14.3 更新範囲とpin

プレイヤーから256以内で活動開始、320より外で休眠可能。このヒステリシスで境界の出入りを安定させる。移動中・ノックバック中・捕獲中・帰還中・飛翔中は、処理が完了するまでactive集合に残す。

遠方をOVERVIEWで映したことだけで、敵が一斉に活動開始しない。遠方の休眠敵は保存位置で描画する。遠方の「待機敵」が活動していないことはP0の仕様であり、見える全員を常時AI更新する必要はない。

少数の敵の移動・衝突・捕獲は60Hz。位相分散するのは将来の低頻度AI判断・非接触装飾だけ。高速個体の衝突を4フレームに1回へ落とさない。

### 14.4 環境アニメと地面小物

環境アニメは `frame = frames[(world_tick//interval + phase)%len(frames)]` 等で表示時に決める。オブジェクトごとのタイマーを全件更新しない。周期は5〜10枚/秒相当を調整候補にするが、60fps描画へ合わせて差分を増やさない。

地面小物はチャンク座標・固定seedから決定し、初回または読み込み時に生成・キャッシュする。Pythonの組み込み `hash(str)` に再現性を依存させず、明示した安定32bit mix等を用いる。描画順や画面外滞在時間で位置が変わらないことをテストする。

初期値は1チャンク1個程度の点・小草。敵、蛇口、イベント進行を乱数配置しない。図形生成を毎フレーム繰り返さない。

### 14.5 計測

目標は512×236で60fps。ただし未実測であり保証値ではない。次をデバッグと計測ログへ出す。

- 総物体数、候補チャンク数、候補物体数、実描画数、active更新数。
- 粒子数、SE要求数／採用数／抑止数。
- 入力所有状態、選択対象ID、プレイヤー状態、敵状態、カメラモード。
- updateと描画処理の所要時間、中央値・p95、固定step数、時間切捨て回数。
- 可能ならWeb側の実表示間隔。ただしPython関数時間とGPU／ブラウザ合成時間を同じ指標と呼ばない。

計測はウォームアップ後30秒以上、同じ入力経路・同じ解像度・同じカメラ区間で比較。通常配置、装飾+128、装飾+512を段階的に試す。ストレス数は達成保証ではない。実機未実施なら「未実施」と記入し、デスクトップ結果を代用しない。

全体の継続的な60fpsと入力の安定性を目標とし、CPU側update+drawのp95が12msを超える場合を調査開始の目安にする。これは仮の予算で、単独の合否保証ではない。処理落ち時はまず装飾・粒子密度を下げ、衝突精度や敵の寿命を変更しない。

## 15. 解像度・UI・Web表示

### 15.1 論理解像度

初期候補：426×196 / **512×236** / 640×294。ユーザー要望はiPhone 16横持ちで粗すぎない画面、PCでは2〜3倍程度。Apple公表のiPhone 16ディスプレイ画素数は2556×1179だが [S3]、これをCSS viewportサイズとして扱わない。ブラウザ枠、拡大設定、Safe Areaにより実際の使用可能領域は異なる。

各プロファイルはアスペクト比をほぼ保つ比較案。起動設定から切替・再起動でよい。ゲーム中の動的な論理解像度変更は不要。比較時にワールド速度や配置を変えない。

同じ水平FOVなら論理幅に比例して投影尺度も変わる。UIの基準寸法は高さ比で補正する。低解像度で固定の極小文字を使って「十分」と判断しない。

### 15.2 表示スケール

CanvasのCSSサイズは縦横比を保ってcontain。横方向と縦方向を異なる倍率で引き伸ばさない。物理devicePixelRatioをワールド座標へ掛けない。PCは内部解像度を変えずに2倍・3倍を選べるようにする。画面に収まらない場合はfitへ戻す。

pixel-art向けのサンプリングを用い、CSSの平滑化でドットをぼかして粗さを隠すことを基本解決にしない。非整数倍率による太さの偏りは実機で比較し、整数倍固定をモバイル全体へ強制して巨大な余白を作らない。

### 15.3 Safe Areaと入力座標

背景は可能な範囲で画面端まで。HUD、文章、アクションボタンはSafe Area内へ置く。`viewport-fit=cover` と `env(safe-area-inset-*)` を利用する方針 [S4]。

ブラウザ側は、実際のCanvas表示矩形 `(left,top,width,height)` と安全領域の交差を論理座標へ変換する。

```text
logical_x = (client_x - canvas_left) * logical_width / canvas_css_width
logical_y = (client_y - canvas_top)  * logical_height / canvas_css_height
```

Pyxelから既に論理座標が返っている入力へ、この変換を再度掛けない。Canvas外・レターボックス内の接触はゲーム操作にしない。Safe Areaはviewport原点からの値であり、中央配置したCanvasの原点と同じと仮定しない。

E0でWeb→Pythonの安全領域伝達がまだ成立していない場合は、ホスト側でCanvas全体を安全領域内に収める暫定表示を許可する。その場合は「全面表示・HUDのみinset」は未完了と記録する。画面端のボタン欠けを黙認して完了扱いにしない。

### 15.4 専用Webホスト

公式にはapp2htmlとHTML Custom Elements等の配布経路がある [S2,S7]。本P0はバージョン固定したランタイムを専用HTMLに組み込み、`.pyxapp` とマップ・設定を同一ビルド成果物として管理する。

採用版で生成したHTMLと公式の組み込み例を確認する。専用の `pyxel-screen` コンテナ等、確認済みの方式を使う。既定の仮想ゲームパッドは本作のドラッグUIと重なるため無効にする [S7]。ローダーURLにバージョン指定がない状態を完成品にしない。

`index.html / manifest.webmanifest / host.css / host.js / game.pyxapp` を基本にする。読み込み、開始、音設定、縦持ち案内、エラー表示を含める。配信は静的ホスト対応。初期ビルドを作ることとGitHub Pagesへ実際に公開することは別で、pushや公開設定変更は許可なく行わない。

### 15.5 Browser枠への対応

通常のSafariタブでアドレスバー等を強制的・常時消去できると約束しない。主な没入表示はホーム画面からのWebアプリ起動とし、Manifestに `display: standalone`、横向き希望、相対的な `start_url/scope` を設定する。iOSのホーム画面Webアプリ動作については公式資料を参照する [S5]。

OSのホームインジケーター、Dynamic Island、丸角までゲームが消せるという仕様にはしない。全画面APIと画面方向ロックはfeature detectionして任意利用し、失敗してもプレイを継続できる。縦持ち時は回転案内と世界停止を行う。

`height:100vh` をフォールバックに、採用環境で使える場合は動的viewport高を利用する。リサイズでレイアウトを再計算する。ゲーム面に `touch-action:none`、選択・コンテキストメニュー抑制を限定して適用する [S6]。ゲーム以外の説明ページまで無条件にズーム不能にしない。

P0はService Worker不要。ホーム画面起動ができても、ネットなしでWASMやフォントまで起動できるとは限らない。完全オフライン対応を確認せずに「オフライン対応済み」と書かない。

### 15.6 UI最小構成

水・電力ゲージ、アクションボタン、近距離の調査マーカー、ポーズ／音設定だけ。常時ミニマップ、長い説明文、常時敵HPは置かない。画面の上下に旧Riversideの固定56/80px帯をそのまま移植しない。

補給不可や捕獲残り時間は記号・小ゲージで分かるようにする。短い操作ヘルプは初回またはポーズ内にまとめる。カラーだけに依存しない。

## 16. 推奨モジュール構成と拡張境界

既存の構成が適切ならそれを優先する。以下のファイルを一字一句作ることは目的ではない。

```text
main.py                        起動、設定読込、Pyxel初期化
jack_world/
  app.py                       update/drawの統合
  config.py                    型付き設定と検証
  model.py                     Player/Buddy/Enemy/Resourceの状態
  math3d.py                     Vec3、カメラ基底、投影、クリップ
  input.py                     InputIntentとポインター状態機械
  collision.py                 AABB、circle、sweep
  world.py                     マップロード、空間分割、active集合
  camera.py                    Follow/Area/Focus/Cue解決
  combat.py                    バリア・泡・電撃・敵状態機械
  interaction.py               調査・補給・モーダル管理
  events.py                    型付きイベント、連番、フレーム内集約
  render.py                    描画キュー、立方体、スプライト、影
  effects.py                   小さな外付け演出
  audio.py                     ゲームイベント→5SE
  platform.py                  Native/Web、visibility、表示領域
  ui.py                        HUD、パネル、debug
assets/                        既存資産または小さな仮素材
web/                           専用ホストとManifest
scripts/                       検証・ビルド・計測
```

小さなファイルを機械的に増やしすぎない。実装量に応じてmodel/events/configやrender/effectsの分割を調整できる。

拡張境界として必要なのは、`PlayerState != PlayerVisual`、`GameEvent != Sound`、`VisibleSet != ActiveSet`、`CameraBase != CameraOverride`、`WorldUnits != LogicalPixels != CSSPixels` の分離である。

外部ライブラリはまずPyxelと標準ライブラリ。テスト・lintは既存環境を使う。新規ならpytest/ruff等を開発依存にできるが、実行ファイルへ重い数値・物理・画像処理依存を追加しない。依存版は検証したものに固定する。

## 17. データロード・エラー処理・再現性

JSONを直接ゲームへ読み込む際は、schema_version、ID重複、対象参照、座標範囲、有限数、enum、負の寿命、負の消費、cap、カメラnear/far、配置の衝突を検証する。付属validatorは初期パックの検査であり、製品ローダーの型検証を置き換えるものではない。

未知の種別は黙って無視せず、ファイル・項目・IDを示して起動エラーにする。ただしエラー時に既存のセーブやデータを上書きしない。設定不備を自動で削って「動いた」ことにしない。

ワールド乱数と演出乱数は分離する。同じseed・同じ入力列・同じ初期設定なら、描画をOFFにしても主要なゲーム状態とイベント列は再現する。装飾の表示順やSE有効無効で乱数消費が変わり、敵の挙動まで変化しないようにする。

デバッグに `reset_scene`、資源最大／ゼロ、敵再配置、カリングON/OFF、解像度プロファイル表示、pan_demoを用意する。リセットはポーズ内から明示操作し、プレイ中のRキー誤押下で無条件実行しない。リセットで捕獲ID・弾・SEキュー・入力所有権をすべて解放する。

## 18. 実装・試験・報告の規約

### 18.1 着手時

現在の作業場所、git status、既存AGENTS/README、実行入口、Python/Pyxel版、Web起動経路、テストコマンドを確認する。古い会話のcommit番号やMac絶対パスをそのまま前提にしない。

既存Riversideの中なら、独立モードと既存テスト維持を優先。空の新規ディレクトリなら最小プロジェクトを作る。無関係な別プロジェクトだった場合、そのコードを上書きせず作業用サブディレクトリへ隔離する。実装を進めた範囲と、元プロジェクトへの統合が未了かどうかを分けて報告する。

### 18.2 ウェーブ運用

詳細は `TASKS.md`。各ウェーブで、実装→自動テスト→起動確認→差分確認→短い報告を行う。ユーザーが最初のウェーブを指示した場合は、指定範囲を越えて残りを自動実装しない。

コミットはリポジトリ固有の方針とユーザー指示に従う。未指示なら差分とコミット候補を報告し、push、公開、ブランチ統合、既存履歴の書き換えを行わない。

### 18.3 受入

`ACCEPTANCE.md` の各項目を、PASS / FAIL / NOT_RUN / BLOCKEDで記録する。自動試験だけではiPhoneの表示・音・指の操作感の確認にならない。スクリーンショットは描画の補助証拠であり、音が鳴ることや入力排他の証拠にはしない。

試験証跡には、ビルド識別子、Python/Pyxel/Webランタイム、端末・OS・ブラウザ、解像度、表示モード、試験日、再現手順を含める。確認できない環境は未確認とする。

### 18.4 P0完了条件

大きな正方形マップの中で、PCとモバイル用入力の基本動作、バディ追従、通常ウニへの防御、泡捕獲と手動電撃、水／電力補給、調査／全景カメラ、SEが一周つながること。

画面外休眠が戦闘・寿命・衝突を壊さず、資源ゼロから補給へ戻れ、操作を離す・アプリを中断することで入力が確実に止まること。完成スプライトの有無でP0を判定しない。

iPhone実機未確認の場合は「デスクトップ上のP0実装完了、モバイル受入は未完了」と明記する。プロトタイプの見た目が簡単であることを、仕様の未実装を隠す理由にしない。

## 19. 今後の拡張のために残すもの

メンダコの少数スプライトへの差し替え、ヒューズの義体デザイン、手書きマップ、夜の省モード、音符などの感情Cue、街の固有調査文、NPCやメンテナンス個体の行動、限定的なカメラ演出追加は可能な境界を残す。

ただし「将来必要そう」を理由に汎用スキルエディター、会話スクリプト言語、汎用物理、巨大な設定ツリーを先に作らない。P0では、**立方体でも『ジャックが止めて、ヒューズが電撃で撃退する』連携が伝わること**と、落ち着いて歩けることを最優先にする。
